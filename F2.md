### 2.2 Core Design Decisions (DO NOT CHANGE)

1. **Tokenizer Strategy:** Using heuristic `Math.ceil(text.length / 4)` for all providers
   - Deterministic mocks for unit tests
   - Real tokenizer integration is optional/future enhancement

2. **Budget Exhaustion:** Graceful fallback, never throw errors
   - `withBudgetHelper()` returns `{allowed: boolean, remaining: number}`
   - Budget exhaustion → template fallback + warning logged

3. **Deterministic Mode:** `--deterministic` sets temperature=0
   - LLM-off mode: zero LLM calls, byte-identical outputs
   - LLM-on + deterministic: structural stability (anchors/factSetIds preserved)

4. **Validator Integration:** Using `MockValidator` from `src/validation/mock-validator.ts`
   - WS-F1 interface frozen: `Validator.validate(draft, factSetIds, metadata)`
   - Outcomes: 'accept' | 'retry' | 'fallback'

5. **Interface Delegation:** All wrappers must delegate to CTS interfaces
   - `summarize()` → delegates to `completions()`
   - `withBudgetHelper()` → delegates to `BudgetTracker.checkBudget()`

## 6. Stage E: Validator Retry Integration (AFTER STAGE D)

### 6.1 Objective
Honor accept/retry/fallback contract from WS-F1 validator per CTS-02 §4.4.

### 6.2 Retry Prompts (CTS-02 §4.4)

**Original (O):**
```
Write a concise paragraph describing TARGET using only FACTS.
Use canonical names; do not add entities, relations, or numbers
not present in FACTS. If unsure, return NEEDS_QUESTION.
```

**Retry #1 (R1):**
```
Output **bullets only**. Use exact canonical names from FACTS
(no synonyms). Include only numbers/enums from FACTS.
No new entities/relations. If missing info, emit NEEDS_QUESTION.
```

**Retry #2 (R2):**
```
Map each FACT to **one bullet** verbatim; no paraphrase;
include entity names **exactly** as in FACTS;
omit anything not in FACTS.
```

### 6.3 Retry Controller Logic

**In `applyLLMPolish()`:**
```typescript
async applyLLMPolish(chunkContext: ChunkContext): Promise<string> {
  let draft = chunkContext.templateDraft;
  let attempt = 0;
  let promptKey: 'O' | 'R1' | 'R2' = 'O';

  while (attempt < 3) {
    // Call LLM with appropriate prompt
    const llmDraft = await this.llmGateway.summarize(
      chunkContext.factSets,
      'spec-ready',
      { prompt: this.getPromptForKey(promptKey), deterministic: this.deterministicMode }
    );

    // Validate
    const result = this.validator.validate(
      llmDraft,
      chunkContext.metadata.factSetIds,
      chunkContext.metadata
    );

    if (result.status === 'accept') {
      this.metrics.llmPolished++;
      return llmDraft;
    } else if (result.status === 'retry') {
      attempt++;
      promptKey = attempt === 1 ? 'R1' : 'R2';
      // Log retry reason
      console.debug(`Retry ${attempt}: ${result.diagnostics[0]?.reason}`);
    } else if (result.status === 'fallback') {
      // Fallback to template
      this.metrics.templateFallback++;
      console.warn(`Fallback for ${chunkContext.entity.id}: ${result.diagnostics[0]?.reason}`);
      return draft;
    }
  }

  // Max retries exhausted → fallback
  this.metrics.templateFallback++;
  return draft;
}
```

## 10. Common Pitfalls & How to Avoid Them

### 10.1 Pitfall: Real API Calls in Unit Tests
**Problem:** Tests try to call real Anthropic/OpenAI APIs, causing failures.
**Solution:** Always mock `completions()` method:
```typescript
vi.spyOn(gateway as any, 'completions').mockResolvedValue('mocked response');
```

### 10.2 Pitfall: Breaking Existing Tests
**Problem:** Changes to generator/CLI break Phase 2/3 tests.
**Solution:**
- Run full test suite after each stage: `npm test`
- Maintain backward compatibility (add optional parameters, not required)
- Check Phase 3 integration tests: `npm test -- src/__tests__/integration/phase3-integration.test.ts`

### 10.3 Pitfall: Forgetting TDD Workflow
**Problem:** Implementing features before writing tests.
**Solution:**
- ALWAYS write failing test first (RED)
- Then implement (GREEN)
- Then refactor
- Commit test + implementation together

### 10.4 Pitfall: Not Following Phase -1 Analysis
**Problem:** Making design decisions that contradict Phase -1 analysis.
**Solution:**
- Re-read `docs/process/grounding.md` before each stage
- Follow established patterns from Stages A & B
- Don't change tokenizer strategy, validator interface, or budget semantics

### 10.5 Pitfall: Missing Coordination with WS-H
**Problem:** Implementing run summary without WS-H input.
**Solution:**
- Create schema proposal BEFORE implementing Stage F
- Document in tracker
- Wait for confirmation
- Update `docs/process/grounding.md` with agreement
