# Phase 5 — Step 5 Implementation Plan  
**Spec Patching & Finalization Summaries**

**Owner:** Phase 5 agent (serial execution)  
**Depends on:** Step 2 (answers attached), Step 3 (ImpactReport), Step 4 (ReanalysisResult with refreshed chunks), existing spec generation infrastructure  
**Blocks:** Step 6 (CLI finalize wiring), Step 7 (end-to-end validation)

---

## 1. Objectives & Scope
- Apply refreshed behavior chunks from Step 4 to existing `spec.md` files, updating only impacted sections while preserving untouched content.  
- Remove resolved QIDs, append deterministic Finalization Summary blocks, and ensure links/anchors remain valid.  
- Maintain deterministic behavior under `--deterministic` and provide diagnostics for patched files.

Out of scope: CLI command surface (Step 6), end-to-end run verification (Step 7), KB serialization (handled alongside Step 4/Step 6).

---

## 2. Inputs & Dependencies
- **Artifacts:**  
  - `ReanalysisResult` (`updatedChunks`, `failedEntities`, warnings, metrics) from Step 4.  
  - `ImpactReport` (seed QIDs, impacted entities/directories/root) from Step 3.  
  - Baseline `spec.md` files generated by earlier phases (root + per-directory).  
- **Architecture references:** CTS-04 §5 (selective re-analysis & patching), Step 0 architecture §3 (Finalization summary requirements), Step 0 summary format decisions.  
- **Existing components:** Spec generator (`MarkdownRenderer`, anchor utilities), KB (for chunk metadata), cross-link validator (for post-patch validation).

## 4. Work Plan (Serial Tasks)

1. **Requirements Review & Data Audit**
   - Revisit CTS-04 §5, Step 0 integration architecture (Finalization Summary format, anchor policy).  
   - Inspect `SpecGenerator.generateDirectorySpecsAsync` and `MarkdownRenderer` to confirm anchor conventions (`<a id="..."></a>`).  
   - Verify availability of anchor → chunk ID mapping (if not, plan to build index).

2. **Patch Engine Design**
   - **Entity → spec mapping:** derive directory path from `entity.path` (e.g., `src/Button.tsx` → `src/`); spec file path is `<directory>/spec.md`. Group impacted entities per spec file; include root spec when `ImpactReport.impactedDirectories` contains root entry.  
   - **Anchor map:** parse spec file lines to construct map `{ entityId → { start: lineIndex, end: lineIndex } }` where `start` is anchor line (`<a id="..."></a>`) and `end` is line before next anchor or next `##` heading or EOF.  
   - **Replacement mechanism:** use deterministic line-based slicing—extract lines between start/end indices and replace with newly rendered chunk text. Preserve surrounding whitespace and headings.  
   - Document invariants: anchor headings unchanged, replacement confined to chunk body; blank lines normalized.

3. **Chunk Replacement Implementation**
   - For each spec file group:
     - Load current content, build anchor map.  
     - For each entity in `updatedChunks` (sorted by entityId):
       1. Fetch entity metadata and refreshed `BehaviorChunk`.  
       2. Render markdown using `MarkdownRenderer.renderEntity(entity, behaviorChunk, { includeHeading: true })`.  
       3. Replace chunk body between anchor boundaries with rendered text (excluding anchor line itself).  
     - For entities in `failedEntities`, leave existing chunk untouched and add warning to report; resolved QIDs remain open.  
   - Rendering automatically omits resolved QIDs (Step 4 chunk already filtered); ensure deterministic formatting by relying on renderer.  
   - After processing all entities, iterate over `ImpactReport.seedQids`:
     - If corresponding entity updated (present in `updatedChunks` and not in `failedEntities`), call `kb.markQIDResolved(qid)` to update KB state.  
     - Skip QIDs tied to failed entities so they remain open.  
   - KB persistence of updated state occurs alongside orchestrator wiring in Step 6.

4. **Finalization Summary Insertion**
   - Locate existing `## Finalization Summary` block after title:  
     - Deterministic mode: replace existing summary entirely (keep single block).  
     - Non-deterministic mode: insert new block after title, shift older summaries downward.  
   - Summary format (sorted alphabetically for determinism):
     ```markdown
     ## Finalization Summary
     - Resolved QIDs: <number>
     - Updated Sections: EntityName (entityId), ...
     - Notes:
       - q:<id>: <short description>
     - Finalized: <ISO timestamp>   <!-- omit line when deterministic -->
     ```
   - `Updated Sections`: entity display name + entityId, comma-separated.  
   - `Notes`: one bullet per resolved QID using trimmed answer text from Step 2.  
   - Separate summary blocks with blank line; ensure deterministic ordering.

5. **Post-Patch Validation**
   - Re-run cross-link validator to ensure anchors intact and QIDs removed align with resolved answers.  
   - Confirm coverage gate still satisfied (exported entities documented or open question).  
   - Verify ImpactReport diagnostics reflected in warnings (cap notes, failures).

6. **Diagnostics & Reporting**
   - Produce `SpecPatchReport` capturing (sorted entries):
     ```typescript
     interface SpecPatchReport {
       patchedFiles: Array<{ path: string; sectionsUpdated: string[] }>;
       failedEntities: FailedEntity[];
       resolvedQids: string[];
       warnings: string[];
     }
     ```
   - Ensure report feeds CLI (Step 6) and finalization summary.

7. **Fixture & Golden Updates**
   - Update `tests/fixtures/phase5/baseline/tiny-react` with before/after spec snapshots (`spec.finalize.before.md`, `spec.finalize.after.md`).  
   - Add golden `finalization.summary.json` capturing summary block contents.  
   - Extend fixture README describing success vs partial-success scenarios, expected warnings/exit codes, and how to run comparison tests.

8. **Documentation & Knowledge Sharing**
   - Update `docs/phase5-finalization-architecture.md` with patch algorithm, summary format, diagnostics.  
   - Provide user guidance snippet for interpreting Finalization Summary blocks.  
   - Log follow-ups (e.g., structured markdown AST approach for future optimization).

## 7. Exit Criteria
- Impacted spec sections replaced with refreshed chunks; unaffected content unchanged.  
- Finalization Summary block appended with accurate counts and notes.  
- Resolved QIDs removed; remaining open questions preserved.  
- Post-patch validations (links, coverage) pass; no regression in deterministic mode.  
- Tests (unit + integration + golden) pass with ≥80% coverage over patching logic.  
- Documentation updated; no open questions blocking Step 6.

---

## 8. Risks & Mitigations
- **Anchor drift:** manual edits may delete or alter `<a id="..."></a>` anchors, preventing chunk replacement. Mitigation: pre-patch validation ensures all required anchors exist; missing ones added to `failedEntities` (`reason: 'anchor-missing'`) with regression tests covering corrupted specs.  
- **Markdown formatting variance:** rely on renderer utilities for consistency; consider AST parse if string replacement insufficient.  
- **Partial successes:** ensure summary notes highlight unresolved entities; CLI will relay via SpecPatchReport.  
- **Partial write failure:** use atomic writes (temp file + rename) to guard against truncated specs; add tests simulating interrupted write.  
- **Concurrent runs:** sequential execution ensures reproducible patches; note eventual need for file-locking if run concurrently.
